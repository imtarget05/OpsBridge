# Accepted-order stall detection

The FlashSale API commits an `inventory.reserved` outbox event before handing an accepted order to the queue. The worker later persists an `Orders` row. ADR-017 gives FlashSale ownership of both records. A reservation older than `Automation:StuckOrder:ThresholdMinutes` with no matching Order is an **accepted order stalled before persistence**. The default is five minutes and the worker scans every 60 seconds; both values are configurable. The bound is therefore threshold plus at most one scan interval under a healthy scanner.

`StuckOrderScanUseCase` queries through an Application port. The EF adapter excludes reservations that have a matching `inventory.released` or `inventory.compensation_failed` event for the same key and correlation ID. It rechecks state immediately before writing an `order.fulfillment_stuck` event. The event ID is derived from the reservation event ID, so the outbox unique index suppresses duplicate alerts from retrying or concurrent scanners. The admin-only `GET /internal/automation/stuck-orders` shows currently unresolved candidates; `POST /internal/automation/stuck-order-scan` runs the same scan used by the worker timer.

This rule is deliberately narrower than all possible fulfillment failures. `PendingPayment` has its own timeout automation. A `Confirmed` order has no subsequent fulfillment-complete transition in the current model, so treating it as stuck would flag every paid order. Separately, `GET /api/outbox/stuck` reports delayed or dead-lettered **event publication**; it does not prove that an accepted order failed to become an Order row. The two runbooks must remain distinct.

Recovery starts with the idempotency key and reservation event ID from the alert. Operators inspect the queue/DLQ and order row, then replay through the existing idempotent worker/DLQ path. The scanner does not mutate inventory or force an order transition. Once the Order row appears, the current-candidate endpoint no longer lists it. An emitted alert remains in the outbox audit trail as the historical detection fact.

Local tests use an injected clock for the deadline boundary, duplicate scans, recovery between query and alert, and exclusion of persisted/compensated reservations. Cloud acceptance still requires a controlled queue outage, an actual alert within the configured bound, one durable alert under repeat scans, successful replay and disappearance from the current-candidate endpoint at the release SHA.
